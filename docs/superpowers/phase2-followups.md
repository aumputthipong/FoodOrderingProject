# Phase 2: งานที่เลื่อนไว้ (follow-ups)

รวบรวมจากการรีวิวทีละ task และการรีวิวทั้ง branch ของเฟส 2 ผู้รีวิวรอบสุดท้ายประเมินว่า**ไม่มีข้อไหนต้องแก้ก่อน merge** (ข้อที่สำคัญถูกแก้ไปแล้วในรอบ fix สุดท้าย)

## ควรทำในเฟส 3 (realtime)
- **request ค้าง:** `api-client` ยังไม่มี timeout ถ้า PATCH ติ๊กรายการค้างเพราะ Wi-Fi ที่ร้านไม่ดี หน้าคิวของแม่ค้าจะไม่รับข้อมูลใหม่จนกว่า request จะจบ ให้ทบทวนตอนเปลี่ยน polling เป็น Socket.IO
- **ตะกร้าเมื่อเมนูหมด:** ฝั่ง client ตัดเมนูที่หมดออกตอนแก้ตะกร้าแล้ว แต่หน้าตะกร้ายังบอกไม่ได้ว่าเมนูไหนหมด เพราะ `CartItem` ไม่มี `status` ควรเพิ่ม field นี้ใน API เมื่อเปิดให้แก้ API
- **toast เมนูหมด:** อาจขึ้นซ้ำถ้ากดรัวระหว่างมี request ค้าง และแถบตะกร้ายังนับเมนูที่ถูกตัดจนกว่าจะ sync ใหม่

## ต้องทำตอน deploy (เฟส 4)
- nginx ยังไม่ส่ง `X-Forwarded-Proto` ต้องเพิ่มพร้อมตั้ง `trust proxy` ของ rate limiter (ดู phase1-followups)
- service `web` ยังไม่มี `restart` policy และ healthcheck
- ล้างข้อมูลที่เกิดจากการทดสอบรับงานใน DB demo (`pnpm db:reset`) ก่อนอัด GIF หรือถ่ายภาพลง README
- E2E ด้วย Playwright บนระบบจริง (การทดสอบรับงานเฟส 2 ใช้การคลิกผ่าน JS ซึ่งไม่ได้ตรวจว่ามีอะไรบังปุ่มหรือไม่)

## UX / accessibility (ทำเมื่อสะดวก)
- รูปร้านใน sidebar ของแม่ค้ายังเป็นกล่องว่างเสมอ
- ลิงก์ "เมนูในร้าน" ไม่ active ตอนอยู่หน้าเพิ่มหรือแก้เมนู
- Switch และ checkbox ตัวจริงเล็กกว่า 44px (แถวที่ครอบใหญ่พอแล้ว)
- `ImageUploadField`: input ซ่อนอยู่ จึงไม่มี focus ring ให้เห็น, ข้อความ error ยังไม่ผูก `aria-describedby`, ข้อความ error เก่าค้างถ้าฟอร์มถูก reset
- ช่องค้นหาหน้าแรกไม่ตาม `?q=` เวลากด back/forward, Skeleton กระพริบทุกครั้งที่ค้นหา (ใช้ `keepPreviousData` ได้)
- สั่งอาหารเสร็จแล้วหน้าตะกร้าว่างแวบหนึ่งก่อนเปลี่ยนหน้า
- สมัครสำเร็จแต่ login อัตโนมัติล้มเหลว ผู้ใช้จะเห็น error และถ้าสมัครซ้ำจะได้ 409
- `main.ts`: `router.isReady()` ยังไม่จัดการกรณี reject

## คุณภาพโค้ดและ test
- ปุ่ม + ที่ค่า 99 ยังส่ง PUT ซ้ำโดยไม่จำเป็น, `quantities` ที่ composable คืนออกมายังแก้ค่าได้ (brief ระบุให้เป็น `Readonly`)
- ถ้ากดเปิด/ปิดขายเมนู หรือติ๊กรายการเดียวกันซ้ำเร็วๆ อาจมี optimistic update ซ้อนกัน แต่ refetch จะแก้ให้ถูกเอง
- test บางตัวยังใช้ selector ที่ผูกกับ DOM ภายในของ reka-ui และบางตัวยัง assert แค่ body ของ request
- ยังไม่มี test ของ: merchant ที่ได้ `redirect` ไม่ปลอดภัย, ปุ่ม logout บนจอเล็กของแม่ค้า, การ sync ตะกร้าหลัง PUT สำเร็จ
